Coal-or-Gift 製作過程技術報告

一款「肌肉聖誕老人發禮物／煤炭」的惡搞瀏覽器小遊戲，從一句想法到可玩成品、含全套美術與入口頁，全程由一位非工程背景的製作人與兩個 AI 協作完成：
Claude Code（寫程式、驗證、整合、審查）＋ Codex CLI（gpt-6-luna，負責生成圖片，並做過一輪程式碼審查）。
這份報告同時是：① 技術紀錄、② 「怎麼和 AI 一起做出一個產品」的教學參考。

2. 製作時間線

階段發生了什麼關鍵決策／學到的事
0. 需求討論使用者只說「想做惡搞風、聖誕老人發禮物給好孩子、煤炭給壞孩子，先跟我討論」。AI 整理核心循環，列出要拍板的 4 件事用「推薦選項＋理由」讓使用者快速決定：網頁版、生命制、連擊觸發雪怪、先用暫代美術
1. 首版原型AI 一次寫出可玩版本：Canvas、WebAudio 合成音效、全部角色用程式畫（暫代）。內建瀏覽器實測「先把玩法做出來，美術後補」，並設計成缺圖自動退回程式繪製，之後可分批換圖
2. 手感與難度使用者要調難度。AI 寫了機器人玩家（新手／普通／熟練）在瀏覽器裡跑整局，量存活時間數據驅動調參；發現「只加速時間會讓高手永遠不死」→ 要同時提高上限
3. 惡搞機制使用者：後期分身擋住目標。→ 分身上限 4、只站兩側；多的改成偽裝成目標的聖誕老人，打到就全螢幕肌肉秀擋 1～2 秒把「後期難度」從「更快更多」換成「更惡搞的干擾」，玩家反感度較低
4. 打擊手感使用者：拋物線怪怪的 → 改短距離直線＋拖尾；主角投擲要有力量感、受擊要有衝擊感加了頓幀、震動、閃白、爆炸擬聲字 → 使用者說震動噁心、有卡頓 → 全部拿掉震動與頓幀，閃白換實作
5. 規則補強發現雪怪失敗沒懲罰（程式 bug）；難度改 1.5～2 分鐘一局；丟錯 3 次扣一顆心使用者用「感覺」找 bug，AI 用程式找根因
6. 入口頁先做輪播 → 使用者澄清想要「背景隨機大圖」→ 重做；新增本機前 5 名排行榜；遊戲內加「首頁」鍵需求常常要「看到才知道」，快速做出來比反覆問更快
7. 美術管線請 Codex 生圖：主角 11 姿勢 → 開場 3 張 → 小孩與怪物 → 偽裝老人 → 圖示 → 12 張入口背景 → Logo見第 4～6 章
8. 畫風大轉彎使用者覺得小孩和怪物「AI 味太重」→ 做風格實驗 → 決定孩子世界改韓系 Q 版見第 5 章
9. 收尾README、讓 Codex 唯讀審查程式碼（2 項，1 項誤報）、修 bug、git commit、主頁改版與扁平 Logo、載入畫面審查結果要逐項驗證，不照單全收

3. 技術架構與重點設計

3.1 檔案結構

index.html        入口頁（背景輪播、排行榜、玩法說明）
game.html         遊戲頁（一個 <canvas>）
js/
  game.js         遊戲邏輯與繪製：狀態機、投擲、目標、連擊、雪怪、肌肉秀、HUD、開場動畫
  sprites.js      程式繪製的備援角色（沒有圖時自動使用）
  art.js          圖片載入器：有圖用圖、缺圖退回；關鍵幀選擇；分身換色
  art_manifest.js 圖片清單（由工具產生）
  entry.js        入口頁：背景輪播、飄雪、排行榜顯示
  scores.js       本機排行榜（localStorage）
  audio.js        WebAudio 合成音效（零音檔）
assets/           sprites/ scene/ ui/ intro/ bg/ anchors.json
tools/            生圖與圖片處理工具、jobs/（生圖工作清單）
docs/             ART_LIST.md、本報告

3.2 設計重點

① 缺圖退回（graceful fallback）——整個專案最有價值的一個設計
所有繪製函式（drawSanta/drawKid/drawYeti/drawItem）一開始先問載入器 Art.xxx()：有正式圖就畫圖並回傳 true，否則落到原本的程式繪製。好處：

  • 美術可以分批交付，每一批放進去遊戲都還能玩。
  • 出圖失敗不會讓遊戲壞掉。
  • 遊戲邏輯（game.js）幾乎不需要知道有沒有圖。

② 圖片清單由工具產生，而不是寫死
tools/build_manifest.py 掃描 assets/ 產生 js/art_manifest.js，遊戲只載入清單內的檔案 → 缺檔不會產生 404 洪水；anchors.json 記錄每張圖的錨點（例如主角「出手那隻手」的位置，投擲物從那裡飛出）。

③ 動畫用「少量關鍵幀整張切換」
使用者明確否決了「拆手臂做骨架」，改成每組動作 2～4 張完整立繪：

  • 主角投擲：待機／蓄力／出手（平射）／出手（向上，依瞄準角度選）。
  • 秀肌肉、歡呼、跳舞各 2～3 張，來回播放。
  • 彈跳、壓扁、左右翻轉、後仰、前撲、閃白、旋轉全部由程式補，所以不需要逐格動畫。

④ 難度曲線用「加速時鐘」
dif() = elapsed × 2.6，所有隨時間變難的參數（生成間隔、停留時間、同時目標數、偽裝老人頻率）都讀 dif()。想把一局從 5 分鐘縮到 2 分鐘，只改一個係數。

⑤ 規則細節（都是和使用者討論＋實測後定的）

  • 3 顆愛心；目標沒處理離開 → 扣心（受傷後 0.9 秒保護期＋場上目標多 1 秒緩衝，避免一次崩盤）。
  • 丟錯：扣 100 分、連擊減半；累積 3 次失誤再扣一顆心；連續打對 10 次可冷卻 1 次。
  • 雪怪能量條與連擊分開計算，連擊管分身和倍率，能量條管雪怪何時出現，這樣連擊中斷不會讓雪怪遙遙無期。
  • 打倒雪怪補一顆心；失敗扣心、扣 500 分、歸零。
  • 偽裝老人：約 20 秒後出現，打到觸發肌肉秀；不打他，他自己溜走並給 +150 分（「識破有獎勵」）。

⑥ 命中判定的手感
先精準判定，沒中再放寬一圈（瞄準輔助）；投擲物短距離直線飛行（約 0.1 秒），總延遲約 0.3 秒。

3.3 效能案例：分身出現時卡頓

  • 現象：玩到一半，分身出現時畫面卡住。
  • 量測：用機器人跑整局並量每幀耗時，發現分身出現的那一幀耗時 170～220 ms。
  • 根因：分身是主角圖換色，用 getImageData 逐像素處理 640×800 的圖，在遊戲進行中「當場計算」，還會強迫 GPU 同步。
  • 修法：①換色用一半解析度；②載入完成後在背景閒置時間預先算好所有版本（一次做一件，讓出執行緒）；③還沒算好就先用原圖，不卡。
  • 驗證：即時玩 45 秒共 4,566 幀，平均 7 ms、最慢 20 ms、零幀超過 25 ms。

教學重點：效能問題要量，不要猜。第一次猜是「ctx.filter 太慢」就改掉了，但真正的元凶是另一個地方。

3.4 「第一秒出現程式畫的聖誕老人」

首次造訪時圖片還在下載，載入器為了不讓遊戲壞掉而退回程式繪製，於是玩家第一秒看到「暫代版」。修法：圖片載完前只顯示載入畫面＋進度條，輸入忽略，超過 12 秒才放行。

教學重點：「容錯機制」本身可能變成使用者看得到的瑕疵，容錯要區分「永遠缺圖」和「還在載」。

4. AI 美術生成管線（Codex）

4.1 為什麼用 Codex CLI、怎麼叫它

使用者一句話：「你直接用 codex cli 調用 codex 看看，模型用 luna，你試試。」

codex exec -m gpt-6-luna -s read-only -C <專案資料夾> --skip-git-repo-check -i 參考圖.png -  < prompt.txt

重點參數：-m 指定模型、-s read-only 沙盒唯讀、-i 附參考圖（可多張）、- 從標準輸入讀 prompt（避免跳脫字元問題）、-o 把最後回覆寫成檔案。

4.2 第一個大坑：Codex 生得出圖，但「存不進專案」

第一次測試成功；第二次要它一次生 10 張並存進專案資料夾，結果它回報「沒有辦法存」。檢查才發現：圖其實生出來了，存在 ~/.codex/generated_images/<session id>/，只是 Codex 自己「複製進專案」那一步常常失敗。

解法：不要叫 Codex 存檔，改由我們自己收。寫了 tools/gen_with_codex.py：

  1. 每一張圖獨立呼叫一次 Codex（可並行 3～6 個），prompt 前面包一層「只生成一次、不要存檔、不要寫程式、回覆 done」。
  2. 從輸出標頭解析 session id:，到對應資料夾找成品。
  3. 驗證成品：尺寸夠大、必須有真正透明的像素（拒絕假透明，見下）。
  4. 複製到專案，失敗自動重試（--retries），可用 --only 名稱,名稱 只重跑指定的幾張。

教學重點：遇到 AI 工具的某一步不穩，不要硬叫它做；把那一步抽出來自己做。

4.3 工作清單格式（可重現、可重跑）

每批生圖是一個 JSON，等於「這批的配方」：

{
  "base_prompt": "共用規則（風格、一致性、透明背景、禁止文字…）",
  "reference": ["assets/_gen/chars_kr/goblin_a_idle.png"],
  "out_dir": "assets/_gen/chars_kr",
  "jobs": [
    { "name": "goblin_a_smug", "reference": ["…可覆寫參考圖…"], "prompt": "這一張的姿勢描述" }
  ]
}

opaque: true 用於全版背景圖（不要求透明）。之後要改 prompt、重生一張，只要改 JSON 再 --only 重跑。

4.4 圖片後處理

工具做什麼
prep_sprite.py裁掉透明邊、依「外框」縮放、腳底貼底；--scale 可固定倍率
build_sprites_kr.py依角色分組套同一個倍率（以該組最高的一張為準，避免有光環/星星的表情被切頭），輸出到 assets/sprites/…
build_manifest.py掃描圖片產生清單，並讀 anchors.json、units.json

4.5 Prompt 設計：有效的寫法

① 共用的「風格＋一致性」前導（base_prompt）

SPRITE for a comedic 2D game, full body, transparent background (real alpha channel),
no ground shadow, no glow, no text, no watermark, ONE character, nothing cropped,
centered, portrait about 2:3.
CONSISTENCY (very important): the attached reference image is the approved design of THIS
character. Draw the SAME character (same face, hair, outfit, colors, proportions, outline
thickness, rendering style) at the same scale and framing as the reference, only changing
the pose/expression described below. Do not add props that are not mentioned.

② 每張只描述「變化的那一點」：
Reformed into a GOOD kid: a sweet smile with no fangs, relaxed eyebrows, big friendly sparkling eyes (no red). A golden HALO floats above the red mohawk. The bat is gone, both hands waving happily. Keep bandana, mohawk and jacket so the contrast is funny.

③ 用「參考圖」鎖定角色：先生一張核准的待機圖，之後所有表情／姿勢都附它當參考。風格也可以用參考圖指定（「Reference 2 shows the exact ART STYLE to use」）。

④ 負面約束要具體：NO belt, NO buckle … exactly like the reference（因為 AI 會自己加腰帶）；no transparent hole, no see-through area（因為愛心中間曾經破洞）；do NOT draw any checkerboard pattern（因為會把假透明的棋盤格畫進去）。

⑤ 圖上盡量不要文字：AI 寫不好中文。標題字由程式疊。唯一例外是 Logo：英文短字，要求「逐字母拼出」並在驗收時逐字確認。

⑥ 解剖學條件直接寫進 prompt：exactly two arms, two legs, five fingers per hand（寫了也不能保證，仍要審查）。

⑦ 構圖要「明說」：入口頁背景要求「低角度仰拍、主角被左邊緣切掉」「蟲眼視角」「俯瞰」「背面」等，才會真的不一樣；沒說的話 AI 傾向都畫成「角色站左或右」。

4.6 假透明與其他圖片陷阱

  • 假透明：生圖工具有時會把灰白棋盤格「畫」進圖裡，整張 alpha 全不透明。→ 工具自動檢查最小 alpha，拒收。
  • 半透明光暈：邊緣的淡淡光暈會讓裁切外框變大。→ 處理時把 alpha 太低的像素清掉再算外框。
  • 角色大小不一致：每張圖獨立縮放會讓同一角色忽大忽小。→ 同一組用同一個縮放倍率。

5. 畫風決策實錄：怎麼把「AI 味」去掉

這段是整個專案最值得教學的部分：風格不是一次選對，而是看過、比過才知道。

5.1 時間順序

  1. 主角（寫實肌肉）：第一張測試圖就被使用者接受：「好像還行，走這個風格」。主角的寫實反差本身就是笑點。
  2. 用同樣風格畫好孩子／流氓／哥布林／雪怪：圖都沒有解剖錯誤，但使用者看了說：「小孩跟怪物實在 AI 味有點太重。有甚麼方法補救？要換畫風嗎？」
  3. AI 先分析原因（過度渲染、每個部位精緻度一樣高、通用奇幻風、縮到 130 像素細節看不到），並列出 5 個補救方向。
  4. 實驗①：壓平濾鏡（程式把顏色壓成 12 色、抹細節）→ 只小幅改善，眼睛還變糊 → 否決，並如實告訴使用者。
  5. 實驗②：叫 Codex 重畫成「西式扁平」（無漸層、統一粗外框、簡化）→ 明顯改善，並排比較圖給使用者看。
  6. 使用者追問：「如果改成比較日系或韓系的扁平畫風呢？」 → 再請 Codex 各畫日系與韓系 3 個角色，四種風格並排（寫實／西式扁平／日系／韓系，旁邊放聖誕老人看搭不搭）。
  7. 使用者：「韓系好了」。

5.2 四種風格的比較（AI 給的判讀）

風格優點缺點
寫實（原本）與主角一致AI 味重，縮小後細節是雜訊
西式扁平縮小最清楚、好壞最好分不是使用者想要的調性
日系好孩子最可愛壞角色細節仍多，整組不統一
韓系貼圖風最乾淨、最統一、AI 味最低壞孩子兇相要靠 prompt 補強（加大紅眼、斜眉、獠牙）

5.3 最終規則（並寫進文件）

聖誕老人「本人」＝寫實肌肉風；孩子世界裡的一切＝韓系貼圖風。

後續衍生出的判斷：

  • 使用者發現偽裝的聖誕老人還是寫實風，和其他目標不協調 → 他是「目標」，要和孩子同世界 → 重畫成韓系 Q 版（保留白鬍子、墨鏡、紅褲、簡化的肌肉）。附帶好處：Q 版混在小孩中更難認，難度設計才成立。
  • 入口頁 12 張背景第一輪畫風忽寫實忽卡通、構圖都是「站左或右」→ 使用者指出「樹深蹲那張差最多（但概念我認可）」→ 重生成：整張圖（含背景）統一成主角的 cel-shaded 風格＋12 種不同構圖。
  • Logo 第一版是立體膨脹風（積雪、岩漿裂縫），使用者「看不清楚，能平面一點嗎」→ 重生成平面版 3 種 → 選「深色底板＋白邊」那版，因為任何背景上對比最穩。

教學重點：

  • 先做小樣本（每種風格 3 個角色）並排比較，不要直接生全套。
  • 讓 AI 說明為什麼不好（診斷），再決定方向。
  • 一個風格規則用一句話寫清楚，之後所有決策都有依據。

6. 品質把關：審查與退回案例

使用者一開始就叮嚀：「我發現生圖有錯（他有三條腿），這種不合理的你要幫我審查喔。」之後每一張圖都被打開檢查，並把這個要求存進專案筆記。

6.1 審查清單

  • 手臂／腿／手指數量與是否融合
  • 臉、鬍子、墨鏡、帽子、服裝與核准參考圖是否一致
  • 不該有的東西（腰帶、上衣、手上拿東西）
  • 構圖：全身是否入鏡、有沒有被裁
  • 背景是否真的透明
  • 表情／姿勢是否符合需求（例如「出手向上」手臂真的向上）
  • 並排縮到實際遊戲大小再看一次（好壞孩子還分得出來嗎？）

6.2 實際被退回的案例

圖問題處理
主角蓄力 windup「透明背景」其實是畫進去的棋盤格，整張 alpha 不透明；姿勢也不像蓄力重生成；工具加上自動拒收假透明
偽裝老人（毛帽版）待機多了腰帶、褲色偏暗prompt 明寫「NO belt」重生成
偽裝老人（毛帽版）再次重生這次變成「圓肚子加胸毛」，腹肌不見了（玩家要靠肌肉辨認）prompt 補「保持六塊腹肌、沒有肚子和胸毛」
偽裝老人（尖耳版）秀肌肉多了腰帶重生成
哥布林 B 待機畫得太寫實（疣、皺紋），與 A 不同風格prompt 補「圓胖、無疣、無紋理」
灰色空愛心中間有透明的洞prompt 補「完全不透明、無洞、無模糊」
雪堆太扁、只剩外框，蓋不住小孩的腳要求「實心白色圓丘、寬是高的 3 倍」
流氓 B 被打中、其他數張連續兩次沒出圖工具自動重試

上表只是節錄；每一批生圖都有一部分要退回或重跑，這就是 AI 生圖的真實品質。沒有審查就不要上線。

7. 驗證方法：沒有測試團隊時怎麼確認東西是對的

方法用在哪為什麼有效
機器人玩家（不同反應速度／手速／失誤率）調難度曲線、驗證規則改動沒打壞平衡在瀏覽器裡「手動推進」遊戲時間，一局幾秒就跑完，可重複上百次。得到：新手約 100 秒、普通約 120 秒、熟練 220～280 秒存活
手動推進＋凍結再截圖檢查特定瞬間的畫面（蓄力、出手、命中、肌肉秀）把 update 換成空函式，用程式設定時間，畫面就停在想看的那一格
逐格量測每幀耗時找卡頓區分「JS 記錄指令」與「真的畫出來」（GPU 是非同步，只量 JS 會誤判）
位置檢查函式目標與分身絕不重疊、目標必須站在地面上規則寫成程式，之後調位置會自動報錯
重現 AI 審查的回報Codex 審查的 2 項發現寫小腳本實際觸發，才知道一項是誤報、另一項是真的但極罕見
兩種視窗尺寸截圖入口頁（桌面 1440×810、手機 375×812）版面問題

重點：能自動重現的就不要靠人眼。「機器人」比人更能暴露平衡問題，但它是完美玩家，所以真人的壽命會更短；最後仍要真人玩。

8. 人與 AI 的協作紀錄

這章是教學的核心：使用者說了什麼 → AI 怎麼理解與行動 → 結果。

8.1 對話節奏（觀察到的模式）

  1. 先討論，再動手：使用者的第一句就是「先跟我討論」。AI 給出推薦選項＋理由，使用者快速拍板。
  2. 每一輪都有「一個明確的下一步問題」，而不是丟一堆選項。
  3. 使用者用「感覺」說話，AI 負責把感覺翻譯成可量測的東西（例如「噁心」→ 震動與頓幀；「卡住」→ 逐幀耗時）。
  4. AI 先做出來再讓使用者看（截圖／並排比較），而不是一直問。
  5. AI 誠實回報限制：看不了 YouTube 影片、沒有實機測試、機器人是完美玩家、某個濾鏡沒用。

8.2 使用者回饋 → AI 動作對照表（節選）

使用者說實際問題AI 的做法
「分身把目標擋住完全看不到」設計問題（後期分身太多）上限 4、只站兩側；多的改成偽裝老人；後來再要求「分身與目標區域直接禁止重疊」→ 重排所有位置＋寫位置檢查函式
「這版有些目標會飛在空中」AI 自己加的「最上排」位置站在地平線上方承認是自己的錯，移除該排，加「不可高於地平線」檢查
「拋物線手感有點奇怪」設計取向改短距離直線＋拖尾，縮短總延遲
「畫面震動太噁心，接近卡死」震動＋頓幀疊加完全移除震動與頓幀；順手把 ctx.filter 閃白改成離屏畫布實作
「受擊壞小孩特別明顯卡頓」煤炭命中頓幀較長＋逐筆濾鏡同上；用逐幀量測確認沒有尖峰
「雪怪擊退失敗沒有懲罰，進度保持最高」真的 bug：用來標記「已砸地」的旗標在登場時就用掉，失敗時永遠不觸發改用獨立旗標；用模擬驗證（扣心、−500、連擊與能量歸零）
「5 分鐘太長，人類專注度撐不住」難度時間尺度加速時鐘 ×2.6，並提高上限讓高手也會死
「分身出現時卡住」即時換色運算背景預先計算＋半解析度
「偽裝老人離開時，主角會發話，很奇怪」對話框的說話者錯了改成偽裝老人頭上浮字
「肌肉秀沒有字有點單調，加點字或別的惡搞元素」（先前說過不要效果字）需求演變加了新聞直播台風格（LIVE、跑馬燈快訊）、對話框、脫落的偽裝、狗仔閃光；把「效果字」和「有笑點的內容字」區分開
「第一秒可能出現 css 畫的聖誕老人」載入階段的容錯變成瑕疵載入畫面＋進度條
「我偷看到分身的皮膚顏色異常」色相偏移把皮膚也轉色改成只換飽和的純紅色（帽子與褲子）；後來發現使用者看到的其實是瀏覽器快取的舊版程式，提醒強制重新整理

8.3 「叫 Codex 畫不同風格」的對話過程（完整示範）

使用者：我覺得小孩跟怪物 AI 味太重。我有甚麼方法補救？要換畫風嗎？
Claude：先診斷原因（過度渲染等），列 5 個方向（只換小孩與怪物成扁平風／壓平濾鏡／全改像素風／請真人畫／回到程式向量角色），並先實測一個便宜的（壓平濾鏡）— 結果不好，如實說。同時停掉正在跑的 28 張批次（避免浪費在可能要換風格的圖上），改做 4 個角色的扁平風樣品。
使用者：（看了並排比較）如果改成比較日系或韓系的扁平畫風呢？
Claude：再請 Codex 各畫日系／韓系 3 個角色，四種並排＋旁邊放聖誕老人，並給出各自優缺點與推薦。
使用者：韓系好了。
Claude：用「韓系待機圖」當新的參考，批次重生成所有表情；並針對壞孩子加強兇相（因為韓系最大的風險是兇不起來）。

這個流程可以濃縮成一條通則：

遇到不滿意 → 讓 AI 診斷原因 → 低成本實驗 → 並排比較 → 人拍板 → 寫成一句規則 → 批量執行

8.4 人與 AI 各自擅長什麼

人（製作人）AI
有沒有梗、好不好笑、噁不噁心寫程式、整合、重構
風格方向與取捨（最後拍板）提供選項、成本、風險、推薦
遊戲手感、玩起來的感受把感受轉成數據並驗證（機器人、逐幀量測）

9. 給想教別人用 AI 的你：可複製的做法

9.1 十條原則

  1. 先討論再實作：第一輪花 5 分鐘定 4 個關鍵決策（平台、結束條件、核心機制、美術策略），比直接動手省很多。
  2. 先用暫代素材把玩法做出來，美術最後換；並從第一天就設計「缺圖退回」。
  3. 把 AI 不穩的環節抽出來自己做（例如 Codex 存檔失敗 → 自己收圖）。
  4. 一個資料夾＋一份 JSON 配方＝可重現：生圖的 prompt 與參考圖放版本控管，要改只改配方再重跑。
  5. 風格要「看過再選」：每種風格先做 3 個角色的小樣本並排比較，不要直接生全套。
  6. 永遠審查 AI 的產出：圖片檢查解剖與一致性；程式碼審查要逐項重現，因為 AI 審查會有誤報。
  7. 把使用者的感覺轉成可量測的東西，並用機器人／逐幀量測驗證。
  8. 每個修改都要驗證：截圖、模擬、量測，不要只說「應該好了」。
  9. 誠實：看不了影片、沒實機、工具沒效就直接說。
  10. 把決策寫下來（最終風格規則、檔案流程、審查標準），之後新增內容就有依據，也方便交接給別人。

9.2 生圖 prompt 骨架（可直接套用）

[用途] SPRITE for a 2D game, full body, transparent background (real alpha channel),
       no ground shadow, no text, ONE character, nothing cropped, centered, portrait 2:3.
[風格] ART STYLE: <一句話風格，附參考圖：「match the attached reference's style exactly」>
[一致性] Draw the SAME character as the attached reference (face, outfit, colors, proportions,
       outline), only changing the pose/expression below. Do not add props not mentioned.
[本張] <只描述這張的變化>
[禁止] NO <常被亂加的東西>; the fill must be fully opaque; do NOT draw a checkerboard.
[構圖] COMPOSITION: <視角、角色大小與位置>（背景／場景圖才需要）

9.3 審查檢查表（印出來貼在旁邊）

□ 肢體／手指數量對
□ 與參考圖是同一個角色（臉、色、服裝）
□ 沒有多出不該有的東西（腰帶、道具、文字）
□ 背景真的透明（放到亮／暗底上都看）
□ 沒被裁到
□ 縮到遊戲實際大小仍然讀得懂（尤其是「好 vs 壞」這類關鍵辨識）
□ 與同組其他圖大小與風格一致

9.4 一個適合教學的專案切法（建議順序）

  1. 需求討論（30 分鐘）→ 2. 最小可玩原型（程式畫）→ 3. 調手感與難度（機器人）→ 4. 加特色機制 → 5. 做「缺圖退回」的美術載入器 → 6. 風格實驗與拍板 → 7. 批量生圖＋審查 → 8. 入口頁與收尾 → 9. 文件、程式碼審查、版本控管。

10. 踩過的坑與限制（誠實版）

AI 生圖

  • 成功率並不高：多手腳、假透明、細節不一致、腰帶亂加、風格漂移，都發生過。
  • 同一個角色的跨姿勢一致性要靠參考圖＋逐張審查，而且仍會偏。
  • 生中文字很差；英文 Logo 這次逐字母驗證才敢用。
  • 一次叫它做很多張會失敗；每張獨立呼叫較穩。

AI 工具鏈

  • 部分指令被內建安全檢查擋下（例如批次刪除含萬用字元的目錄），需要人手動執行。AI 不應繞過。
  • 截圖會「慢一拍」（顯示的是前一個畫面），要等一下或重拍才可信。
  • 瀏覽器快取舊程式造成「我改了但你看到沒改」的誤會；改完要強制重新整理。
  • 預覽瀏覽器視窗的自動暫停機制（切換分頁就暫停）會干擾自動化測試，要在測試時關掉。
  • AI 程式碼審查有誤報：這次兩項裡有一項照它描述的情境重現不出來（但旁邊真的有個相關漏洞）。

驗證的限制

  • 機器人是完美玩家，真人壽命會更短。
  • 手機只用瀏覽器模擬過，沒有實機測試。
  • 我無法觀看 YouTube，只能看使用者貼的截圖。
  • 慢速網路下的載入畫面是靠邏輯確認，沒有實際在慢網路上看過。

還沒做的

  • 背景音樂、遊戲背景（夜晚雪地）與命中擬聲字的圖像化、手機實機優化、上線發佈。
